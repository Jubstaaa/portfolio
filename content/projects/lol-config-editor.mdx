## **What It Is**

![Sound settings read from a live League install](/images/projects/lol-config-editor/lol-config-editor-sound.webp)

League keeps its settings in `Config/PersistedSettings.json` — two files' worth of `name = value` pairs, one for `Game.cfg` and one for `Input.ini`. This app reads that file, renders it as controls, and writes it back, changing only the keys you touched.

It covers effectively the whole file: every volume and interface option, combat text, minimap, scoreboard, chat, emotes, the item shop, and all 176 keybinds across both slots League keeps for each action.

The point is switching. Save a setup under a name — _Ranked_, _ARAM_, _Guest_ — and apply it later in one click. Settings are per machine, so every account on that PC picks them up.

---

## **The Problem Underneath**

**League only saves what differs from its own defaults.** A fresh config is missing most keys entirely.

The first version addressed settings with JSONPath strings evaluated against form state, which meant it could only edit a key that was already in the file. Anything absent resolved to an empty path and the control silently did nothing — so most of the settings screen was unreachable, and adding new options mostly produced dead checkboxes.

The rewrite addresses settings by `(file, section, key)` and writes through an upsert that inserts the file, section or key when it is missing. Each control also carries League's own default, so a setting you have never touched in game still shows the right value and becomes editable.

## **Keybinds**

![Every cast mode for every ability, both slots](/images/projects/lol-config-editor/lol-config-editor-hotkeys.webp)

League writes a binding as `[Ctrl][Button 1],[<Unbound>]` — two slots per action, each a chain of bracketed tokens.

Taking a key means freeing it everywhere else first. The original did that with a `String.replace` over the serialised config, which fails twice: it replaces only the first match, so a key bound in three places stays bound in two; and it matches substrings, so binding `[Button 1]` corrupts an existing `[Ctrl][Button 1]` into `[<Unbound>][Button 1]`.

Bindings are now parsed into chords and compared structurally. A modified chord is a different key, and every slot holding a conflict is cleared.

Browser events also needed translating. The DOM numbers mouse buttons from zero and puts the middle button second; League numbers from one and puts the right button second. Passing `event.button` straight through mislabelled every button on the mouse.

## **Architecture Notes**

- **Finding the install** reads `RiotClientInstalls.json`, which Riot's own launcher writes on both platforms, rather than guessing at `C:\Riot Games` — the default, and wrong for anyone who installed elsewhere.
- **Locking** solves the real complaint: League rewrites the settings file every time it exits, which is how hand-edited configs get lost. The app can mark the file read-only, and applying settings still works while locked — it unlocks, writes, and locks again.
- **The chosen path** lives in Tauri state and is read on every command. Caching it at startup meant picking a new folder mid-session left Apply writing to the old one until restart.
- **The settings model is pure** — read, upsert, keybind parsing and the catalogue never import a Tauri command. CI has no League install, so the tests run against a real config the game wrote, checked into the repo as a fixture.
- **The catalogue is tested against that fixture.** A control pointed at a key League does not have fails the build instead of silently doing nothing — which is exactly how the item-component checkbox shipped broken, bound to a key that exists in neither section.
- **Updates install in place**, signed with the project's own key, so they never pick up the macOS quarantine flag that makes a downloaded build look damaged.
